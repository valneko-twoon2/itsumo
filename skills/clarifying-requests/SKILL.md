曖昧な依頼を、推測で進めない。ただし、聞きすぎない。**聞くのは、答えによって作るものが変わる点だけ。**

## 1. 聞く前に、自分で調べる

聞く前に、次で分かることは自分で確かめる。

- コード、既存の文書、`AGENTS.md`、設定、`git log`。
- 既存の似た実装（`/itsumo:following-existing-code`）。
- 直前のやり取りでユーザーが言ったこと。

調べても分からない点だけを、聞く候補にする。

## 2. 聞く点を決める

候補ごとに、次の 2 つを考える。

| 問い | 答え | どうする |
|---|---|---|
| 答えによって、作るもの・変える場所・手順が変わるか | 変わる | **聞く** |
| | 変わらない、または後で簡単に直せる | 既定を選んで進み、報告に「こう仮定した」と書く |
| 間違えたとき、取り返しがつかないか（削除、公開、課金、データの書き換え） | つかない | 上の通り |
| | つく | 必ず聞く |

## 3. 聞き方

`AskUserQuestion` ツールを使う（無い環境では、同じ形で文章で聞く）。

- 1 回に最大 4 問。関連する点はまとめて聞く。
- 各問は、2〜4 個の選択肢。**推奨を最初に置き、「（推奨）」と添える**。各選択肢に、選ぶと何が起きるかを 1 文で書く。
- 質問は具体的に。「どうしますか」でなく「ログイン失敗時は、エラーを画面に出す／ログだけに残す／再試行を促す、のどれにしますか」。
- 「進めていいですか」のような、結果が変わらない確認はしない。
- 選択肢に無い答えを書けるようにしておく（「その他」）。

## 4. 回答が曖昧なら、深掘りする

ユーザーの回答、特に**自由記述の回答**は、また曖昧なことがある。受け取ったら毎回、次を確かめる。

進捗のチェックリスト:

```
- [ ] 回答は、作るものが決まる具体さか（何を・どこに・どの基準で）
- [ ] 回答の中に、新しい曖昧な言葉（「いい感じ」「ちゃんと」「もう少し」）が残っていないか
- [ ] 回答どうしや、既存のコードと矛盾していないか
```

- 曖昧さが残っていれば、**その回答の言葉を引用して**、より具体的に聞き直す（選択肢を添えて）。
  - 例: 回答「もっと見やすく」→「見やすくは、文字の大きさ／余白／色のコントラスト／情報の並び替え、のどれを指しますか」
- 聞き直しは、作るものが決まるまで続ける。一度聞いたことを繰り返さない。回答で決まった点は、確定として扱う。
- 聞き直しが 3 回続いても決まらないときは、そこまで分かったことを短くまとめて、「ここまでをこう理解した。この通りでいいか」と確認する。
- 残った曖昧さが、結果を変えないほど小さくなったら、聞くのをやめる。残りは既定で進み、仮定を報告に書く。

## 5. 決まったら

- 決まった内容を、1〜3 行で言い直してから作業を始める（食い違いを早く見つけるため）。
- 作業中に新しい分かれ道が出たら、2 章の基準でもう一度判断する。

入力: 「ログイン画面をいい感じにして」

出力（1 回目の質問）:

```
Q1. 「いい感じ」で直したいのは、どれですか。
  - 見た目（余白、色、文字の大きさ）（推奨）: スタイルだけを直す。動作は変えない
  - 使いやすさ（入力の流れ、エラー表示）: フォームの動作も変える
  - 両方: 範囲が大きくなるので、順に進める
Q2. 既存のデザイン（他の画面）に合わせますか。
  - 合わせる（推奨）: 他の画面のスタイルを手本にする
  - 新しいデザインにする: 方針を先にください
```

自由記述の回答が「もう少し分かりやすく」だった場合、続けて:

```
「分かりやすく」を、もう少し具体的にしたいです。次のどれに近いですか。
  - エラーメッセージの文言を具体的にする
  - 入力欄にラベルと例を付ける
  - ボタンの名前や配置を変える
```
