大きな作業を一度に書き上げない。**計画→合意→段階ごとに実装・確認・コミット**の順に進める。何を作るかが曖昧なら、先に `/itsumo:clarifying-requests` で決める。

## 1. 大きな作業かどうか

次のどれかに当たれば、このスキルで進める。当たらなければ、計画を書かずに進めてよい。

- 触るファイルやモジュールが多い（目安: 5 つ以上、または層をまたぐ）。
- 公開された形（API、DB のスキーマ、設定、ファイル形式）が変わる。
- 途中で止めると、壊れた状態が残る。

## 2. 計画を書く

コードを読んで（`/itsumo:following-existing-code`）、次の形で計画を書き、ユーザーに見せる。

```
目的: 何ができるようになるか（1〜2 文）
範囲: 含めるもの／含めないもの
影響: 触るファイル・モジュール、変わる公開された形、移行が要るデータ
段階:
  1. <段階の名前>: 何をするか。どう確かめるか。
  2. ...
リスク: 壊れうるところ、迷っている点、代替案
```

段階の分け方:

- **各段階の終わりで、全体が動く**こと（テストが通り、ビルドできる）。途中で壊れた状態をコミットしない。
- 1 段階は、1 つのコミットにできる大きさ。レビューする人が一度に読める量にする。
- 順番は、土台から（型やスキーマ → 中心の処理 → 呼び出し側 → 画面）。古い仕組みを消すのは、新しい仕組みに切り替えた後の最後の段階。
- 公開された形を変えるなら、新旧を併存させる段階を挟む（呼び出し側を順に移してから古いほうを消す）。
- 危ない段階（データの移行、削除）は分けて、`/itsumo:handling-destructive-operations` に従う。

**合意を取ってから実装を始める。** ユーザーが計画を直したら、計画を書き直して確かめる。

## 3. 段階ごとに進める

進捗のチェックリスト（段階ごと）:

```
- [ ] この段階の範囲だけを実装した（/itsumo:making-minimal-changes）
- [ ] テスト、型チェック、ビルドが通った（/itsumo:running-regression-tests）
- [ ] コミットした（/itsumo:committing-changes）
- [ ] 計画と違うことが起きていない（起きたら、次の段階に進む前に計画を直して伝える）
```

- 計画に無い作業が必要になったら、勝手に足さずに、計画を直してユーザーに伝える。小さく、計画の目的の範囲内なら、報告に書いて進めてよい。
- 長い作業は、計画と進み具合を文書（例: リポジトリの `docs/plans/<名前>.md` か、ユーザーが決めた場所）に残すと、中断しても再開できる。残すかどうかはユーザーに確かめる。

## 4. 報告

段階ごとの結果（コミット）、計画から変えた点とその理由、残っている作業。

入力: 「認証をセッションから JWT に移行して」

出力（計画）:

```
目的: API の認証を、サーバーのセッションから JWT に置き換える。
範囲: API の認証のみ。画面のログインフォームとユーザーの DB は変えない。
影響: src/auth/、src/middleware/auth.ts、全 API のルート（12 ファイル）、環境変数 JWT_SECRET の追加。
段階:
  1. JWT の発行と検証を src/auth/jwt.ts に足す。単体テストで確かめる。
  2. 認証のミドルウェアを、セッションと JWT の両方を受けるようにする。既存のテストが通ることを確かめる。
  3. ログイン API が JWT も返すようにする。
  4. 画面の API 呼び出しを JWT に移す。E2E で確かめる。
  5. セッションの処理を消す。
リスク: ログイン中のユーザーは、段階 5 の後に再ログインが要る。トークンの失効方法（ブラックリストか短い有効期限か）は決めたい。
```

依頼: $ARGUMENTS
