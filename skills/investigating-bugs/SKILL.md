**原因を突き止めるまで、直さない。** 症状を消すだけの修正（例外を握りつぶす、`null` の確認を足して通す、待ち時間を足す）は、原因を残し、後で別の形で壊れる。

直し方の範囲は `/itsumo:making-minimal-changes`、直した後の確認は `/itsumo:running-regression-tests`。

## 1. 手順

進捗のチェックリスト:

```
- [ ] 1. 症状を正確に言い直した（何をしたら・何が起き・本来は何が起きるはずか）
- [ ] 2. 再現した（手順、またはテストで落ちるのを見た）
- [ ] 3. 原因の仮説を 2 つ以上挙げた
- [ ] 4. 証拠で仮説を絞り、原因を 1 つに確定した
- [ ] 5. 原因を直した（症状ではなく）
- [ ] 6. 再現手順で、症状が消えたことを確かめた
```

### 1〜2. 症状を言い直し、再現する

- エラー文は**全文**を読む。スタックトレースは一番下（呼び出しの根）と、自分のコードが出てくる最初の行を見る。
- 再現できないうちは直さない。再現の手順が分からないなら、ユーザーに聞く（入力、環境、頻度）。
- 不具合を捕まえる**失敗するテスト**が書けるなら先に書く。直した後に通れば、再発防止にもなる。
- 「前は動いていた」なら、`git log` や `git bisect` で壊した変更を探すのが早い。

### 3〜4. 仮説を絞る

- 仮説は 1 つに決め打たない。最初に思いついたものが違うことは多い。
- 仮説ごとに、**当たっていれば見えるはずのもの**を決め、実際に見る（ログ、変数の値、実行の流れ、設定、バージョン）。コードを読むだけで決めない。
- 見る手段は、小さく試せるものから: 値の出力、デバッガ、最小の再現コード、入力を半分にして切り分ける。見るために足した出力は、後で消す。
- 同じ症状を出す場所が複数あるなら、全部挙げてから絞る。
- **想定と違う結果が出たら、仮説を捨てる。** 結果に合わせて仮説を曲げない。

### 5〜6. 直して、確かめる

- 直すのは原因。症状を隠す変更（握りつぶし、再試行、待ち時間）は、原因が本当にそれのときだけ。
- 再現手順をもう一度やって、症状が消えたことを確かめる。テストを書いたなら、通ることを見る。
- 同じ種類の不具合が他の場所にもないか探し、見つけたものを報告する（直すかどうかは `/itsumo:making-minimal-changes` の範囲に従う）。

## 2. 手を止めて聞くとき

- 再現できない、または環境（本番、実機、権限）に依存して調べられない。
- 原因の候補が 3 回の確認を経ても絞れない。いままでに分かったことを書いて、ユーザーに次の手を相談する。
- 原因が、依頼の範囲を超える設計の問題にある。

## 3. 報告

症状、再現手順、原因、直した内容、確かめた方法の順に短く。確かめられなかったものは「未確認」と書く。

入力: 「保存ボタンを押すと 500 エラーになる」

出力:

```
症状: 保存ボタンで POST /api/items が 500。
再現: 名前が空のまま保存する。
原因: items.ts の validate が空文字を通し、DB の NOT NULL 制約で例外になる。
直した内容: validate で空文字を拒み、400 を返すようにした（1 行）。
確認: 同じ手順で 400 が返ることを確かめた。空以外の保存は変わらない。
```
