**測らずに速くしない。** 推測で直した場所は、遅さの原因ではないことが多く、読みにくくなるだけで終わる。順番は、**基準を測る → ボトルネックを特定する → 1 つ直す → 測り直す**。

直し方の範囲は `/itsumo:making-minimal-changes`、動作が変わっていない確認は `/itsumo:running-regression-tests`。

## 1. 基準を取る

進捗のチェックリスト:

```
- [ ] 何が遅いかを、操作・データの量・環境で言えた
- [ ] 目標を決めた（決まっていなければ聞いた）
- [ ] 同じ手順で何度も測れる方法を用意した
- [ ] 基準の数値を、複数回測って記録した
```

- 「遅い」を、測れる形にする: どの操作が、どのデータ量で、何秒かかるか（メモリなら何 MB か）。曖昧なら聞く。
- 目標が無いと、やめどきが無い。「許容できるのは何秒か」を聞く。
- 測る条件を揃える: 本番に近いビルド（リリースビルド、最適化あり）、同じデータ、ウォームアップ後。1 回の値を信用せず、数回の最小値か中央値を使い、ばらつきも見る。
- 測る道具は、プロジェクトに既にあるもの（ベンチマーク、`time`、アプリのログ）から始める。無ければ、最小の計測コードを足す（後で消す）。

## 2. ボトルネックを特定する

- **プロファイラや計測で、時間（メモリ）の大半がどこで使われているかを見る。** 読んで当たりを付けた場所を、そのまま直さない。
- 例: Node.js は `--cpu-prof`、Python は `cProfile` や `py-spy`、Rust・C は `perf` やフレームグラフ、ブラウザは DevTools の Performance、SQL は `EXPLAIN`（実行計画）、ビルドは各ツールの時間表示。
- 候補は、効果が大きい順に見る: 無駄な処理の繰り返し（同じ計算、N+1 のクエリ）、不要な I/O や通信、アルゴリズムの計算量、データ構造、巨大なデータの丸ごとの読み込み。細かい書き換え（ループの微調整など）は最後。
- 時間の大半を占める所が見つからないなら、計測の粒度を細かくする。

## 3. 直して、測り直す

- **1 回に 1 つだけ変える。** 複数を同時に変えると、どれが効いたか分からない。
- 変えるたびに、基準と同じ方法で測り直す。**効果が測れない（ばらつきの範囲）変更は戻す。**
- 動作を変えない。テストを通し、結果が同じことを確かめる。キャッシュを足すなら、古い値が残る条件（無効化の時機）を確かめる。
- 読みにくくなる最適化は、効果が大きいときだけ入れ、理由をコメントに 1 行書く。
- 目標に届いたらやめる。届かず、残りが設計の問題（大きな書き換えが要る）なら、止めてユーザーに相談する。
- 計測のために足した一時的なコードは消す。ベンチマークを残すかは、ユーザーに聞く。

## 4. 報告

前後の数値、測り方と環境、変えたこと、効果が無く戻したもの、確かめていないこと。

入力: 「一覧画面の表示が遅い」

出力:

```
基準: 商品 5,000 件で表示まで 3.2 秒（5 回の中央値。リリースビルド）。目標は 1 秒以内。
原因: プロファイルで 2.6 秒が、各行の getPrice() の中の DB 問い合わせ（5,000 回）だった。
直したこと: 価格をまとめて 1 回の問い合わせで取る（src/list.ts の 12 行）。
結果: 0.7 秒（同じ条件、5 回の中央値）。テスト 41 件成功。
効果が無く戻したもの: 行の描画の memo 化（差は測定のばらつき以内）。
未確認: 本番のデータ量（50 万件）での時間。
```
