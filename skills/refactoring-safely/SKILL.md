リファクタは**振る舞いを変えない**変更。外から見た結果（戻り値、出力、例外、副作用、公開された関数の形）が変わったら、それはリファクタではない。

頼まれていないリファクタはしない（`/itsumo:making-minimal-changes`）。このスキルは、ユーザーがリファクタを頼んだときの進め方。

## 1. 始める前に

進捗のチェックリスト:

```
- [ ] 目的を 1 文で言える（例: 「300 行の processOrder を、検証・計算・保存の 3 つに分ける」）
- [ ] 範囲を決めた（触るファイルと、触らないもの）
- [ ] 今の振る舞いを守るテストがある。無ければ先に足した
- [ ] テストが今、全部通ることを確かめた
```

- **テストが無いなら、先に書く。** 今の振る舞いをそのまま記録するテスト（入力と、今の出力）でよい。今の振る舞いが不具合に見えても、ここでは直さず記録する。
- 公開された形（他のモジュールや外部が使う関数名・引数・型・ファイル形式）を変えるなら、その範囲をユーザーに確かめる。
- 目的に要らない改善（命名の好み、別の流儀への書き換え）は範囲に入れない。

## 2. 小さく進める

1 段階につき、種類が 1 つの変更にする。

| 段階の例 | 1 段階の大きさ |
|---|---|
| 改名 | 1 つの名前とその参照すべて |
| 関数・メソッドの抽出 | 1 つの塊を 1 つの関数に |
| 移動 | 1 つのモジュールを新しい場所へ（参照の直しを含む） |
| 重複の統合 | 同じものを 2 か所から 1 か所へ |

各段階の後に:

1. テスト、型チェック、リントを走らせる（`/itsumo:running-regression-tests`）。
2. 落ちたら、その段階を直すか戻す。次の段階に進まない。
3. 通ったら、段階ごとにコミットする（`/itsumo:committing-changes`、接頭辞は `refactor:`）。

**混ぜない:** 途中で不具合や改善点を見つけても、その段階では直さない。メモして、リファクタが終わってから別のコミットにするか、報告する。テストの期待値は変えない（変えないと通らないなら、振る舞いが変わっている）。

改名や移動には、エディタやツールの機能（言語サーバーの rename、`git mv`）を使う。文字列の一括置換は、関係ない一致（文字列、コメント、別の同名）を巻き込むので、使ったら差分を全部読む。

## 3. 終わる前に

- 最初に決めた目的を満たしたか。範囲の外を触っていないか（`git diff --stat`）。
- テストの期待値を変えていないか。変えたなら、その理由（振る舞いが変わった）を報告し、リファクタと分ける。
- 最初に足した、振る舞いを記録するテストは残す。

## 4. 報告

目的、段階の一覧（コミット）、走らせた確認、見つけたが直していないもの。

入力: 「`order.ts` の `processOrder` が長すぎる。分割して」

出力:

```
目的: processOrder（280 行）を、検証・計算・保存に分ける。公開された形は変えない。
準備: 振る舞いを記録するテストを 6 件足した（tests/order.test.ts）。
段階:
  1. refactor: 入力の検証を validateOrder に抽出
  2. refactor: 金額の計算を calcOrderTotal に抽出
  3. refactor: 保存を saveOrder に抽出
確認: 各段階で npm test -- order と tsc が通った。
直していない気づき: 送料が 0 円のときの分岐が到達しない。別に直すか判断してほしい。
```
