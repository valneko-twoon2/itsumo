依存は、入れた時点から保守の負担になる。**足す前に要るかを確かめ、上げるときは小さく、確かめながら**進める。

新しいコードの書き方は `/itsumo:following-existing-code`、確認は `/itsumo:running-regression-tests`、脆弱性の扱いは `/itsumo:reviewing-security-boundaries` の依存関係の行。

## 1. 追加する前に

進捗のチェックリスト:

```
- [ ] 既存の依存や言語の標準機能で足りないことを確かめた
- [ ] 候補の保守状況・ライセンス・推移的な依存の量を見た
- [ ] プロジェクトのパッケージマネージャで入れる（ロックファイルで判定）
- [ ] 入れる理由を報告に書ける
```

- 同じことをする依存が既にないか、標準機能や数行の自前のコードで済まないかを先に探す。
- 候補は、最終更新、公開されている不具合、ライセンス、推移的な依存の数を見る。小さな機能のために大きな依存を入れない。
- パッケージマネージャは、ロックファイル（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`uv.lock`、`Cargo.lock` など）で決める。別のものを混ぜない。
- 用途が開発だけなら、開発用の依存に入れる。
- 迷うとき、新しい依存が大きいときは、候補と理由を示してユーザーに聞く。

## 2. 更新するとき

- **1 回に 1 つの依存（か、同じ系統の依存）だけ**上げる。全部を一括で上げない（`npm update` や `cargo update` を引数なしで走らせない）。
- 上げ幅は最小にする。目的（脆弱性の修正、必要な機能）に足りる版までにし、最新に上げるのは頼まれたときだけ。
- メジャーバージョンを上げる前に、変更履歴やリリースノート、移行ガイドを読み、**壊れる変更を書き出す**。使っている API を検索して、影響する箇所を挙げる。
- 上げる前に、テストが通る状態であることを確かめる。落ちているものがあれば、更新のせいと区別できない。
- ロックファイルは**手で書かず**、パッケージマネージャのコマンドで更新する。衝突したときも再生成する。

## 3. 上げた後に

進捗のチェックリスト:

```
- [ ] 導入、ビルド、型チェック、テストが通った
- [ ] 監査コマンドの結果を、上げる前と比べた
- [ ] git diff --stat で、意図しない依存や大量のロックファイルの変更が無い
- [ ] 破壊的な変更の影響箇所を直した
```

- 落ちたら、依存の変更を戻すか、影響箇所を直す。テストを弱めて通さない。
- 脆弱性の指摘は、本番の依存か開発だけか、その部分を呼んでいるかを調べて報告する。`--force` 付きの一括修正（`npm audit fix --force` など）はしない。
- 直せない指摘（修正版が無い）は、そのまま報告する。
- 依存の更新は、機能の変更と別のコミットにする（`chore:`）。

## 4. 報告

何を、どの版からどの版へ。理由。確認した結果。確かめていないもの。

入力: 「axios を最新にして」（現在 0.27、最新は 1.x）

出力:

```
変えたもの: axios 0.27.2 -> 1.7.2（メジャー）。
破壊的な変更: 変更履歴から、既定のエラーの形と、ヘッダーの渡し方が変わる。src/api/client.ts の 2 か所を直した。
確認: npm ci、tsc、npm test（84 件成功）。npm audit は 3 件から 1 件に減った（残りは開発用の依存で、修正版が無い）。
未確認: 本番のプロキシ越しの通信。
```
