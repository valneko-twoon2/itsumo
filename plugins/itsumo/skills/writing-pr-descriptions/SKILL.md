PR の説明は、**レビューする人が、コードを開く前に全体を掴める**ことが目的。コミットの書き方は `/itsumo:committing-changes`。

## 1. 書く前に

1. 材料を集める: `git log <基準>..HEAD --oneline` と `git diff <基準>...HEAD --stat`（基準は既定ブランチ）。コミットメッセージを並べるだけにしない。**差分全体**を読んで書く。
2. リポジトリに PR のテンプレート（`.github/pull_request_template.md` など）があれば、**それに従う**。このスキルの形は、テンプレートが無いときの既定。

## 2. 形

タイトル: コミットの 1 行目と同じ決まり（プロジェクトの接頭辞の流儀に合わせ、72 文字以内、句点で終えない）。

本文:

```
## 概要
何を変えたか。1〜3 文。

## 背景
なぜ必要か。依頼、不具合、関連する課題（Issue）。

## 変更点
- 主な変更を、レビューする順に 3〜7 項目。ファイルを全部は挙げない。

## 確認
- 実行したコマンドと結果。確かめていないものは「未確認」と書く。

## 見てほしい点
- 判断に迷った箇所、影響が広い箇所、代替案とその理由。
```

- 言語はプロジェクトに合わせる（直近のコミットや PR を見て決める）。
- 「確認」には、実際に走らせたものだけを書く。走らせていないものを「問題なし」と書かない（`/itsumo:running-regression-tests`）。
- 関連する Issue があれば `Closes #123` のように書く。
- 範囲を超える変更が混ざっていたら、分けることを提案する。

## 3. 書いた後に

- 本文は一時ファイルに書き、`gh pr create --title "..." --body-file <ファイル>` で渡す（引用符や改行の崩れを避ける）。
- **署名行を付けない。** 「Generated with Claude Code」や `Co-Authored-By` を入れない（itsumo のフックが、付いていれば実行前に止める）。
- 作る前に、`git status` で未コミットの変更が無いことと、ブランチが push 済みかを確かめる。PR を作るのは、ユーザーに頼まれたときだけ。

入力: 「PR を作って」（`calcTax` の端数を切り捨てから四捨五入に直したブランチ）

出力:

```
タイトル: fix: calcTax の端数を四捨五入にする

## 概要
税額の端数処理を切り捨てから四捨五入に変えた。

## 背景
請求書の合計が、端数の切り捨てで 1 円ずれる問題（#42）。

## 変更点
- src/price.ts: calcTax の Math.floor を Math.round にした
- tests/price.test.ts: 端数が .5 のケースを足した

## 確認
- npm test -- price: 8 件成功（修正前は新しいケースが失敗）
- 請求書の画面での表示は未確認

## 見てほしい点
- 既存の請求データの再計算はしていない。必要か判断してほしい
```
