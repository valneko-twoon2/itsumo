テストケースの選び方（同値分割、境界値、状態遷移、デシジョンテーブルなど）は `/itsumo:designing-test-cases`。プロジェクトに独自の手順（`docs/verification.md`、`CONTRIBUTING.md`、影響範囲を選ぶスクリプト）があれば**そちらを優先**する。

## 1. 変える前に

- 変える振る舞いの既存テストを探して読み、何を守っているかを理解する（隣の `*.test.*` / `*_test.*` / `test_*.py`、`tests/`・`e2e/`・`__snapshots__/`、Rust の `#[cfg(test)]`）。
- 速度のための変更や、速度を落としうる変更（起動、頻繁に呼ばれる処理、通信）は、前後で測る。

## 2. テストを変更と一緒に変える（同じコミットで）

| 変更 | テストですること |
|---|---|
| 機能の追加 | 新しい振る舞いを守るテストを足す。正常系に加えて、失敗・空・境界のどれか 1 つ以上 |
| 不具合の修正 | 修正前に落ち、修正後に通るテストを足す（再発防止）。先にテストを書いて落ちるのを見る |
| 仕様の変更 | 古い振る舞いを前提にしたテストを新しい仕様に書き直す。実装に合わせて期待値を機械的に変えるだけにしない |
| 機能やコードの削除 | その機能だけを確かめていたテストと、使われなくなったフィクスチャ・モック・補助関数を消す |
| 名前の変更や移動 | テストファイル、テスト名、`describe` も一緒に動かす |

テストファイルも 1 つの責務に保つ。足すことで別の領域が混ざる、または 500 行を大きく超えるなら、領域ごとに分ける。

意味を失ったテストを残さない。触った領域で次のものを見つけたら消すか直す:

- もう無い機能・分岐・オプションを確かめるテスト
- 何も確かめないテスト（アサーションが無い、常に通る）
- 他のテストと同じことを確かめる重複
- 理由の無い `skip`・`only`・無視指定
- 消した画面・型・出力のスナップショット、フィクスチャ、基準画像

テストを消したら、何を・なぜ消したかを報告に書く。**落ちるからという理由だけでテストを消したり弱めたりしない。**

## 3. 影響する範囲だけを走らせる

**変えたコードと、その呼び出し元・依存先・共有部品から選ぶ。** 「念のため」に全テスト・全 E2E・ビジュアル回帰へ広げない。全部を走らせるのは、影響の広い変更（共有部品、型やスキーマなどの契約、ビルド設定、依存関係）、ユーザーが求めたとき、衝突を解いた直後の最終確認のときだけで、その理由を報告に書く。

影響するテストは、テストランナーの機能で見つける（Vitest の `related`、Jest の `--findRelatedTests`、pytest の `--lf` や `-k`、Rust の `--test <name>` と名前での絞り込み、Go のパッケージ指定）。無ければ、変えたモジュールを import・参照するファイルを検索して、そのテストを選ぶ。

毎回するもの: 型チェック（あれば）、変えたファイルのリントとフォーマッタ。

道具が見落とすもの（実行時に読むファイル、別のモジュール経由で届く統合テスト、別の名前の E2E）は自分で足し、何を・なぜ足したかを報告に書く。

## 4. 退行を疑う場所

- 型・スキーマ・API の契約を変えたら、両側（送る側と受ける側）、モック、呼び出し元が揃っているか。
- 共有部品を変えたら、それを使う他の機能が壊れていないか。
- 不具合を直したら、同じ種類の不具合を他の場所（他の画面、他の種類、他の言語）でも探し、いくつ見つけて直したかを報告に書く。
- 実環境に依存する変更（外部サービス、GPU、実機、デスクトップアプリ、ブラウザの描画）は、単体テストが通っても確かめたことにならない。実環境で確かめるか、「未確認」と報告する。実環境で動かすときは、ユーザー自身のデータ・プロセス・設定に触れない分離した環境（専用のデータフォルダ、プロファイル、ポート）で動かし、自分が起こしたものだけを後で止める。

## 5. 完了を宣言する前に

「直した」「できた」「動く」と言う前に、**実行して確かめる**。コードを読んで「動くはず」と判断しない。

進捗のチェックリスト:

```
- [ ] 頼まれたことを、実際に動かして確かめた（テスト、ビルド、型チェック、実行のどれか）
- [ ] その実行の結果（コマンドと出力の要点）を報告に書ける
- [ ] 確かめられなかったものを「未確認」と分けた
- [ ] 失敗を見たら、直して同じ確認をやり直した
```

- 確かめるものは、頼まれた**振る舞い**。「ビルドが通る」だけで「機能が動く」と言わない。不具合の修正なら、元の症状が出なくなったことを、再現した手順で確かめる。
- 確かめる手段が無いとき（実機、外部サービス、権限が足りない）は、できなかったと書き、ユーザーが確かめる手順を添える。
- 結果が想定と違ったら、報告の前に原因を調べる。通ったように見える部分だけを選んで報告しない。

入力→出力の例。

入力: ログインの不具合を直した。`npm test -- auth` を走らせて 12 件通った。
出力: 「ログインの不具合を直した。`npm test -- auth` が 12 件成功（修正前は `rejects expired token` が失敗していた）。ブラウザでの実際のログインは未確認。」

## 6. 報告

- 走らせたコマンドとその結果、その対象を選んだ理由、走らせなかったものとその理由。
- 足した・変えた・消したテストとその理由。テストを変えなかったならその理由（例: 文書だけ）。
- 見た目の変更は、見られたテーマや画面サイズを言い、見られなかったものは「未確認」と書く。
- 成功・失敗・未実行を分ける。見ていない範囲について「問題なし」と言わない。
- 落ちたテストは調べて直す。スナップショット・フィクスチャ・基準画像は差分を読まずに更新しない。既存の失敗で今回と無関係だと言うなら、その証拠（変更前で落ちること）を示す。
