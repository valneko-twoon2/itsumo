チェックは `node "${CLAUDE_PLUGIN_ROOT}/lib/docs-check.mjs"`（Node.js 18 以上と Git が要る）。フォルダと上限はプロジェクトの `.claude/itsumo.json` の `docs` で変えられる（既定は `docs/architecture`、`docs/design`、入口 7000 バイト、他 14000 バイト）。itsumo の SessionStart / SubagentStart フックはマップの入口ページ（既定 `docs/architecture/README.md`）を毎回の最初に差し込むので、組み込みの Explore や Plan のサブエージェントにも届く。

## 1. アーキテクチャマップ: 短く、正しく

マップは作業の最初に読まれるので、**コード検索では分からないことだけ**を持ち、全部を読める小ささに保つ。ファイルを 1 行ずつ並べた大きなマップは読まれず、すぐ古くなる。ファイルは検索の方が速く見つかる。読まれる価値があるのは、部品のつながり方、何が正か、どこから始めるか。

| 入れる | 入れない |
|---|---|
| 部品のつながりと向き（層、契約、処理の流れ） | フォルダのファイル一覧（Glob や grep で出る、古くなる） |
| 値・型・設定の正がどこにあるか | 正から写した値・契約・設定 |
| よくある変更の「どこから始めるか」 | 名前で分かるファイルの説明 |
| 名前から分からないフォルダ（`derive`、`finish` など）の役割 | 「最終更新」の行（git にある） |
| 境界がそこにある理由を 1 行で | ファイルの中の変更 |

- パスはリポジトリのルートからバッククォートで書く（`src/state/queue.ts`）。機械が実在を確かめられる。似たファイルが多いフォルダは役割と共に 1 度だけ挙げる。
- 入口ページ（`README.md`）は全体、どこから始めるか、トップレベルのフォルダすべて。詳しい領域は 2〜4 枚の別ページに。ページのツリーにはしない。
- **変えるとき**: 同じコミットで、部品（トップレベルのフォルダ、パッケージ、層、機能フォルダ、ルール、スキル、ランチャー）の追加・削除・移動、境界や依存の向きの変更、「どこから始めるか」の行が正しくなくなったとき。既存フォルダへのファイル追加やファイル内の変更は書かない。
- 上限を超えたら、検索で分かること（ファイル一覧）を削る。ページを増やさない。どのページにも合わない新しい領域は、ページを足す前にユーザーに聞く。

## 2. 設計ページ: 機能ごとの今の仕様

`docs/design/` は各機能が**今**何をするか（振る舞い、作り、セキュリティ境界、既知の制限）を持つ。機能を変える前に読み、変えた後に直す仕様。毎回は読まない（それはマップ）。なぜそう決めたかは書かない（git の履歴が持つ）。

```text
---
covers:
  - src/service/queue.ts
  - src/engine/**
---
# 題名
1 段落: 何のための機能か
## Behaviour / 振る舞い       今の仕様を現在形で、事実だけ
## Boundaries / 境界          この機能のセキュリティ境界（表: 境界 | 守り）
## Known limits / 既知の制限
## Not implemented / 未実装   本当に無いものだけ
```

- `covers` はそのページが記述するコード: ファイル、フォルダ、グロブ（`dir/**` はフォルダをまたぐ、`*` はまたがない）。変えたファイルからページを見つける手がかりなので正確に保つ。各項目はどれかのファイルに当たらなければならない。
- コードと照らして、コードがすることを書く。予定は書かない。値・契約・設定は写さず、どこにあるかを名指す。
- 1 ページ 1 機能。上限を超えたら機能で分ける（フロントとバックで分けない: 1 つの機能の両半分は同じページ）。新しい機能にはページと、索引 `docs/design/README.md` への 1 行を足す。
- **読む**: コードを変える前に `node "${CLAUDE_PLUGIN_ROOT}/lib/docs-check.mjs" --find <path>...` で、変えるファイルを扱うページを出して読む。
- **直す**: ページを正しくなくする変更（振る舞い、境界、制限、機能の部品の増減）と同じコミットで。境界の変更（API、権限、CSP）にはページの更新を伴わせる。ページが正しいままの関数内の変更は何もしない。

## 3. ユーザー向けの文書

ユーザーに見える機能を足す・変える・消すときは、ユーザー向けの文書（マニュアル、README の使い方、ヘルプ）を**同じ変更で**直す。

| 変更 | 文書ですること |
|---|---|
| 新しい画面・ダイアログ・操作 | 該当する章に説明を足す。見せたい画面があれば図を足す |
| 見た目や操作の変更 | 該当する章の説明を直す。スクリーンショットの撮り直しはユーザーに確かめてから（重い・環境に依存するため）。古いままなら「図は未更新」と報告する |
| 画面の文言の変更や削除 | 文書が画面の文言を引用・参照していれば直す |
| 機能の削除 | 説明と図を消す |
| 画面に出ない変更（内部の整理、不具合修正） | 直さない |

- 確かめた事実だけを書く。実環境が要る振る舞いは、コードと文言から確かめたことだけを書き、推測を書かない。読むのはユーザーなので、識別子や内部の名前を出さない。
- 画面の部品は画面に出る言葉で呼ぶ（多言語なら各言語のカタログの言葉）。
- 文書が多言語なら、主言語を先に書き、他の言語は同じ構造（見出し、段落、表の行数、図の順）で後から一括で訳してよい。訳していない章は分かるように残す（`/itsumo:localizing-ui-text`）。

## 4. 機械の確認

`docs-check.mjs` が落とすもの: マップの入口ページが触れていないトップレベルのフォルダ、マップと設計ページ（と索引）が挙げる実在しないパスやリンク、上限を超えたページ、`covers` の無い・どのファイルにも当たらない設計ページ、索引に載っていない設計ページ。`--staged` は、設計ページが扱うコードをステージしたのにそのページがコミットに無いとき**警告**する（落とさない: 関数内の変更ならページは正しいままのことが多い）。pre-commit フックに `--staged` を入れておくとよい。

ページの中身が正しいかは分からない。ページを変えたら、変えたところの前後の段落を読み直し、正しくなくなったものを直す。

## 5. 文書を作り始めるとき

1. マップ: `git ls-files` でトップレベルを見て、`docs/architecture/README.md` にトップレベルのフォルダそれぞれの 1 行、部品のつながり、正の場所、「どこから始めるか」の表を書く。7000 バイト以内。
2. 設計ページ: 変更の多い機能から 1 枚ずつ。全部を一度に作らない。
3. `docs-check.mjs` を通す。

## 6. 報告

直したページと理由、または直す必要が無かった理由。`docs-check.mjs` の結果。撮り直していない図や、訳していない言語。
