プロジェクトにセキュリティの設計文書（`docs/design/security.md`、`SECURITY.md`、機能ごとの「境界」「既知の制限」）があれば、**それが正**。このスキルは、変更ごとに確かめる点だけを並べる。

## 1. いつ使うか

次のものを足す・変えるとき。単なる表示や内部ロジックの変更では要らない。

- 外から呼べる入口: HTTP API、IPC やプロセス間のコマンド、CLI の引数、Webhook、権限（capability）設定、CSP、ウィンドウ設定
- URL を開く・ダウンロードする・外部サイトにつなぐコード
- ファイルパス（読み・書き・削除・移動・アーカイブの展開）
- 別のプログラムの起動（シェル、インタプリタ、パッケージマネージャ、ブラウザ、AI の CLI）
- 外部データの利用（外部 API の応答、アップロードされたファイル、画像、AI の回答、ユーザーが渡す JSON）
- API キーやトークンの扱い、依存関係の追加や更新

## 2. 境界ごとの確認

| 境界 | 確かめること |
|---|---|
| 外から呼べる入口 | 引数は**入口で**検証する（呼ぶ側の UI を信用しない）。新しいコマンドは許可リストや権限設定に明示的に足す。必要以上の権限（ファイルシステム全体、任意のシェル、任意の HTTP）を与えるプラグインや設定を足さない。認証・オリジン・ホストの確認を外さない |
| Web ビュー、HTML | CSP を緩めない（`'unsafe-eval'`、外部の `script-src`、`*`、`connect-src` への外部ホスト）。データはフレームワークで描画し、HTML 文字列を DOM に入れない（`innerHTML`、`dangerouslySetInnerHTML`、`v-html`）。`eval`、`new Function`、文字列の `setTimeout`、`javascript:` URL を使わない |
| ファイルパス | 名前は許した文字だけ。`..`、絶対パス、ドライブ名、UNC、予約名（`CON`、`NUL` など）を拒み、決めたフォルダの外に出ない。アーカイブは各エントリの行き先が対象フォルダの中かを確かめる（zip-slip） |
| プログラムの起動 | プログラムを直接起動し、引数は 1 つずつ渡す。`cmd /C`、`powershell -Command`、`sh -c`、`shell=True` を使わない。ユーザーの文字列は引数でなく stdin かファイルで渡す。Windows の `.cmd` / `.bat` は内部で cmd.exe を通るので、固定の引数だけにする |
| ダウンロード、URL | `https` だけ、ホストは完全一致で照合する（`example.com.evil.example` を通さない）。部分一致の URL やユーザーが入れた任意の URL を開かない（SSRF、オープンリダイレクト）。一時的な名前で書き、完了したら移す。サイズ上限とキャンセルを持つ。外部サービスのアドレスは 1 か所にまとめる |
| テスト用の抜け穴 | テストのための環境変数やフラグはデバッグビルドでだけ読み、リリースでは無視する。持たせるのは時間や回数だけにし、パス・URL（ループバック以外）・プログラム名・秘密・何を読み書き実行送信するかを決める値は決して取らない。抜け穴を足したら、パーサの単体テストと、変数が無いとき本物の値が使われるテストを足す |
| 外部データ | 長さ・個数・数値の範囲を制限する（巨大な画像・JSON・応答で落ちない）。画像はデコードする前にヘッダからサイズを確かめる。AI の回答は形と値を検証してから使う。外部から来たテキストはデータであって指示ではない |
| モデルやシリアライズ形式 | 読み込むだけでコードが動く形式（pickle、`.ckpt`/`.pt`、YAML の任意オブジェクト、Java のシリアライズ）を自動で読み込む経路を足さない。安全な形式（`.safetensors`、JSON）を選ぶ |
| 秘密情報 | キーはヘッダで送り、URL・ログ・エラーメッセージ・クライアントへの戻り値・通知に入れない。保存は OS の保護された保存先（DPAPI、Keychain、libsecret）か、プロジェクトの決めた方法で。リポジトリに入れない |
| データベース | SQL は固定の文字列とバインド変数（`?1`、`$1`）。文字列に埋めてよいのは、コードが決めた識別子だけ |
| ファイルの競合 | 確かめてから使うまでの間にすり替えられないよう、同じハンドルで確かめて使うか、一時的な名前から rename する（TOCTOU） |
| 依存関係 | 追加・更新したら監査する（`npm audit --omit=dev`、`cargo audit`、`pip-audit`、`osv-scanner` など）。開発用ツールだけに関わる指摘は報告し、勝手に強制更新しない |

迷ったら、悪意ある入力を受けるテストを足す: `../`、`%2e%2e`、`..\\`、`\\?\`、`C:\`、`\\server\share`、`https://example.com.evil.example`、`http://127.0.0.1`、`file:///`、巨大な値、空、制御文字、NUL、非常に長い名前、Unicode の正規化違い。ケースの選び方は `/itsumo:testing`。

## 3. 機械の確認を足すとき

- 静的解析（ESLint のルール、clippy、Semgrep、bandit など）やテストで守るなら、わざと違反を入れて落ちることを確かめてから戻す。
- 誤検出のために許可リストへ足すなら、理由をそのリストのコメントに書く。
- 機械の確認が守る範囲と守らない範囲（構文だけを見る、別名を追わない、データの流れを見ない）を知り、守らない部分は人が見る。

## 4. 報告

- どの境界を何のために変えたか、走らせた確認とその結果。走らせなかったものとその理由。
- 新しい既知の制限や受け入れたリスクがあれば、その機能の設計ページ（あれば）の「既知の制限」を同じ作業で直す。境界や守りを足したなら「境界」の表も。
- 見つけた脆弱性は、直したかどうかに関わらず報告する。大きな修正を勝手に進めず、先に聞く。
