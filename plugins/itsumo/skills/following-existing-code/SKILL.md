新しく書くコードは、**このリポジトリの既存コードの続き**に見えるようにする。書き始める前に手本を探す。

既存のコードを直すときの範囲は `/itsumo:making-minimal-changes`、テストの扱いは `/itsumo:running-regression-tests`。

## 1. 書く前に、手本を探す

1. まず、プロジェクトの決まり（`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`.editorconfig`、リンタやフォーマッタの設定）を読む。既存コードと食い違うときは、決まりが正。食い違いは報告する。
2. 書くものと**同じ役割の既存コード**を、検索で 2〜3 個見つける（隣のファイル、同じフォルダ、同じ種類のモジュール）。1 個だけだと、そのファイルだけの癖を手本にしてしまう。複数あれば共通点が分かる。
3. 手本を読み、次を書き出す。

| 見るもの | 例 |
|---|---|
| 置き場所と名前 | フォルダの切り方、ファイル名、関数・変数・型の命名規則 |
| 構造 | 1 ファイルに何を入れるか、層の分け方、公開する関数の形 |
| エラー処理とログ | 例外か戻り値か、使うエラーの型、ログの書式 |
| 使う道具 | 既にある共通関数、ユーティリティ、HTTP や DB のクライアント、テストの道具 |
| 書き方の癖 | 非同期の書き方、型の付け方、コメントの量と言語、import の順 |
| テスト | 置き場所、名前、準備の仕方、モックの使い方 |

## 2. 書いている間

- **既にあるものを再実装しない。** 共通関数やヘルパー、既存の依存で足りるなら、それを使う。新しいライブラリは足さない。足りないときだけ、理由を添えて聞く。
- 既存と違う流儀が一般には「よりよい」ときも、既存に合わせる。流儀そのものを直したいなら、別の依頼として報告する。
- 手本が見つからないとき（新しい種類のコード）は、いちばん近い既存コードに合わせる。新しい流儀を持ち込むなら、その理由を報告に書く。
- 手本を丸ごと写さない。名前や中身は、書くものに合わせて変える。

## 3. 終わる前に

進捗のチェックリスト:

```
- [ ] 手本にした既存コードを 2〜3 個挙げられる
- [ ] 命名、構造、エラー処理、テストの書き方が手本と同じ
- [ ] 既にあるヘルパーや依存を使い、同じものを作り直していない
- [ ] 新しい依存や新しい流儀を持ち込んでいない（持ち込んだなら理由を書いた）
```

## 4. 報告

手本にした既存コード（パス）と、合わせた点を 1〜2 行で。

入力: 「`products` の API エンドポイントを足して」。同じフォルダに `users.ts` と `orders.ts` がある。

出力:

```
手本: src/api/users.ts、src/api/orders.ts
合わせた点: ファイル名、zod での入力検証、AppError を投げるエラー処理、tests/api/ の置き方
```

依頼: $ARGUMENTS
