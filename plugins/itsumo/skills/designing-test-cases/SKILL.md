このスキルはケースの選び方だけを扱う。どのテストを変え・走らせるかは `/itsumo:running-regression-tests`、外からの悪意ある入力は `/itsumo:reviewing-security-boundaries`。

## 1. 今あるものを読む

1. コードの隣のテストと、同じ領域の統合テストを開く。`*_edge_cases.*`、`*_failures.*`、`mutation_*` のような名前のファイルは、以前に穴が見つかった場所を示す。
2. 変更が触るものを挙げる: 入力、上限、`if` や `match`/`switch`、組み合わせた条件、状態、規則。1 つ 1 行で、作業メモか報告に。

## 2. 項目ごとに技法を選ぶ

| 項目 | 技法 | 書くケース |
|---|---|---|
| クラスのある入力（種類、モード、名前の形、空か否か） | 同値分割 | 有効・無効の各クラスから代表を 1 つずつ。クラスの結果をアサートする |
| 上限のある数・サイズ・長さ・個数・時間幅 | 境界値 | 最小、その 1 つ下、最大、その 1 つ上、0 や空。日付なら現地時刻の 0 時ちょうど、タイムゾーンや夏時間の境目 |
| `if` や `match` | 分岐網羅 | 両方の結果 |
| `&&` や `\|\|` の条件 | 条件網羅 | 各部分が真と偽に少なくとも 1 回ずつ。データやセキュリティを守る条件（パス、URL、サイズ）なら、その部分だけが違い結果が変わるべき対のケースも |
| 外から来るテキストやデータ（パス、URL、巨大・空の値、制御文字） | エラー推測、次にプロパティベース | 敵対的な値（`/itsumo:reviewing-security-boundaries` の一覧）をケースに入れる。ランダム入力は fast-check、Hypothesis、proptest、QuickCheck など |
| 段階、状態、ライフサイクル | 状態遷移表 | 3 節 |
| 2 つ以上の入力が一緒に決める | デシジョンテーブル、ペアワイズ、全列挙 | 4 節 |

## 3. 状態の変化（キュー、インストール、ジョブ、注文など）

テストを書く前に、コードの中の遷移を読む。推測で表を作らない。

1. まず遷移表を作る。行は今の状態、列はイベント（開始、完了、失敗、キャンセル、再試行、クリア、再起動など）。各セルは「X に移る」「何もしない」「拒否（エラー）」。この表がテスト計画になる。
2. データ（状態、メッセージ、時刻）を変える正当な遷移ごとに 1 テスト。ユーザーが到達できる拒否・何もしないセルごとに 1 テスト（完了した項目のキャンセル、待機中の項目の再試行）。テストしなかった何もしないセルとその理由は報告に書く。
3. 保存される状態なら、遷移が再起動を越えて残るか確かめる（実行中だった項目が再起動でどうなるか）。
4. 保存に失敗したとき、半端な状態が残らないか確かめる。
5. 遷移がイベントや通知を出すなら、変わった項目についてそれをアサートする。
6. ジョブを待つのに sleep を使わない。イベントか状態を待つ。最も競合しやすいのは実行中のキャンセルなので、偽の実行環境でテストし、最終状態をアサートする。
7. フロントエンドのモックが同じ状態を持つなら、状態を変えたらモックも同じ作業で変え、モックの遷移が表と合うかもテストする。

## 4. 複数の入力で決まる規則

1. 規則が読む入力と、その水準を挙げる。同値クラスから始める（例: モードは A・B・C・その他、マスクは無し・空・有効、元画像は無し・有り）。
2. コードの中の規則を見つける（入力を検証する関数、組み立て前のチェック、分類関数）。属性が 1 つなら分割で足り、いくつかが一緒に決めるならデシジョンテーブルが要る。

| 規則の形 | 技法 | 方法 |
|---|---|---|
| いくつかの条件で結果が違う（メッセージ A で拒否、B で拒否、受理） | デシジョンテーブル | 規則ごとに 1 行。列は各条件（真・偽・関係なしの "-"）と結果。関係ない条件の行はまとめる |
| 独立したオプションがいくつかあり、不具合が 2 つの組から生じる | ペアワイズ（全ペア） | どの 2 つのオプションの水準の組も、少なくとも 1 ケースに現れる。被覆表をテストの中に表として書く。ペアは 2 オプションの不具合しか捕まえないので、3 オプションの不具合がありうるならそう言う |
| オプションも水準も少ない | 全列挙 | 直積が小さければ全部書く |
| 多くのオプションに依存する出力（生成物、組み立てたリクエスト） | 代表ケースとスナップショット | 規則の分岐ごとに 1 組み合わせで要の部分をアサートし、少なくとも 1 つは出力全体のスナップショットも |

- ペアワイズの表は、生成ツールのためだけに依存を足さず、手で書いてよい。
- 規則の行ごとに 1 テスト、規則にちなんだ名前で（例: 「マスクは inpaint と outpaint 以外では拒否する」）。
- 個数の上限は、最大が受理され 1 つ多いと拒否されることをアサートする。
- 敵対的な組み合わせを入れる: マスクを持ってはいけないモード、送ったリストと合わない個数（クライアントは信用しない）、範囲外の重みや幅。
- スナップショットは差分を読んでから更新する。
- 規則が網羅されたと言えるのは、すべての行にテストがあるとき。テストの無い行とその理由を挙げる。

## 5. ケースを書く

1. テストはファイルの流儀に合わせ、振る舞いにちなんで名付ける。上限なら「上限ちょうどは受理し、1 つ多いと拒否する」の形。
2. 結果（値、エラーの種類、状態、イベント）をアサートし、ログ行や内部の呼び出しはアサートしない。
3. そのケースが、名前の言う理由で落ちることを確かめる。上限なら、演算子を変えれば落ちなければならない。
4. 既知の不具合は、期待失敗のテスト（`it.fails`、`xfail` など）として理由のコメント付きで残す。プロパティテストの回数やシードは固定し、深い一回きりの実行はコマンドラインで変え、コミットする既定値は変えない。

## 6. ケースが届く範囲を確かめる

- カバレッジツールが測るのは主に行・分岐・関数。条件網羅、MC/DC、同値クラス、境界値は測られないので、それには報告のケース表が証拠になる。
- 1 ファイルだけのカバレッジを見る（例: `npx vitest run <test> --coverage.enabled --coverage.include=<src>`、`pytest --cov=<module> <test>`）。そのために全スイートを走らせない。
- ケースが本物の変更を捕まえるかは、ミューテーションテストの道具（cargo-mutants、Stryker、mutmut、PIT など）で確かめられる。

## 7. 報告

- 項目ごとに: 技法とテスト名。変えたセルに印を付けた遷移表。行ごとにテストのあるデシジョン表やペア表。
- ケースの無い項目やセルとその理由。
- 走らせたコマンドとその結果、走らせなかったもの。
